## §1 프로젝트 개요

- **핵심 과제**: 사용자가 업무 질문을 입력하면 관련 문서를 검색해 확인 가능한 출처와 함께 답하거나, 근거가 부족하면 그렇다고 안내하는 Knowledge Agent를 팀으로 만든다.
- **강조점**: 기능 수보다, 어떤 업무 문제를 얼마나 신뢰성 있게 해결했는지를 원본 결과로 설명하는 것이 중요하다.
- **필수 범위**: 업무 문제 정의 / 문서 수집·정제·청킹·메타데이터 / BM25+Vector 검색 결합 / re-ranking / 캐싱 또는 쿼리 리라이트 중 1개 / 질문–정답–근거 평가셋 / 비교 실험 / 실행 인터페이스 / 재현 문서·발표
- **선택 범위**: 최적화 두 가지 모두 적용 / HyDE / 대화 메모리 / 메타데이터 기반 접근 통제 / 추가 검색 지표 / 웹 배포
- **기본 환경**: Python·LangChain 중심(수업 환경 연장). 임베딩 모델·벡터 저장소·생성 모델·reranker는 실행 가능성과 사용 조건을 확인해 팀이 고른다.
- **실행 인터페이스**: Streamlit 또는 기존 웹 화면/API 중 1개. 질문·답변·근거·오류를 확인할 수 있으면 충분하고 UI 완성도는 경쟁하지 않는다.
- **주요 산출물**: GitHub 저장소, 문서 목록·전처리 코드, 평가셋, 실행별 검색·답변 기록, 비교 보고서, 시연 자료

## §2 시작 전 준비

1. Python, Git/GitHub, API 개발, 「RAG 파이프라인 설계」 수업 내용을 복습한다.
2. 수업 환경에서 생성 모델 호출 1건과 임베딩 생성 1건을 실행해 모델명·버전·오류 여부를 확인한다.
3. 작은 문서 1개를 청크로 나누고 청크 ID·문서 ID·원문 위치를 연결해 저장해 본다.
4. BM25 결과와 벡터 검색 결과를 각각 출력하고, 두 점수의 척도가 다르다는 점을 설명할 수 있어야 한다.
5. 공개 문서 또는 가상 문서를 준비하고 이용 조건과 외부 모델로 보내도 되는지 확인한다.

## §3 프로젝트 목표

- G1. 사용자의 업무·정보 탐색 어려움과 오답 위험을 정의하고 RAG를 쓰는 이유를 설명한다.
- G2. 원문과 연결된 청크·메타데이터를 만들고 BM25+Vector 하이브리드 검색과 re-ranking을 구현한다.
- G3. 검색 근거로 답하고, 근거가 부족하면 무리하게 답하지 않는다.
- G4. 캐싱 또는 쿼리 리라이트를 적용하고 품질·지연·운영 조건의 trade-off를 비교한다.
- G5. 고정 평가셋으로 검색 품질과 답변 품질을 구분해 측정하고 개선·실패 원인을 설명한다.

학습 연결(참고): 파일 입출력·예외 → 문서 처리·실행 기록 / Git → 설정·평가셋 버전 고정, 브랜치·PR·리뷰 / SQL → 문서·청크·버전 메타데이터 저장 / FastAPI·Pydantic·캐싱 → 질문·응답 규격과 캐시 정책 / LangChain·구조화 출력 → 출처 포함 응답, 형식 검증 / RAG 설계 → 수집–청킹–색인–검색, 결합·재정렬, 평가.

## §4 전체 흐름

문제·성공 기준 정의 → 문서 및 평가셋 준비 → Vector Baseline → 하이브리드 검색 → re-ranking → 최적화 → 고정 평가 → 실패 분석·재현·시연

### §4.1 STEP 1. 문제와 성공 기준 정의
- `docs/problem.md`에 사용자, 기존 탐색 과정, 질문 범위, 오답·근거 부족의 영향, RAG 선택 이유, 제외 범위를 쓴다.
- 품질·시간·비용 우선순위와 팀 목표값은 **결과를 보기 전에** 정한다.
- 개선 전 업무 소요시간을 측정하지 않았다면 절감률을 실제 성과처럼 주장하지 않는다.

### §4.2 STEP 2. 문서·청크·평가셋 확정
- 정제·청킹·색인 재생성 절차를 구현하고 청크 크기·겹침·모델·색인 버전을 기록한다.
- 평가셋은 **총 30문항**: 개발용 10문항 + 최종 평가용 20문항, 질문 ID로 분리한다.
  - 개발용 10: 답변 가능 8, 근거 없음 2
  - 최종용 20: 직접 검색 10, 표현 변형·유사 조건 구분 7, 근거 없음 3
- 답변 가능 문항 필드: ID, 유형, 질문, 기대 답변의 핵심 사실, 허용 근거 문서/청크, 원문 위치
- 근거 없음 문항: 정답은 "정보 부족 안내", 근거 ID는 비우고 부재 판정 이유를 적는다.
- 최종 평가 질문은 개발·튜닝에 쓰지 않고 실행 전에 버전을 고정한다.
- 원문이 색인에 들어가는 것은 정상이지만, **정답표를 검색 문서에 섞거나 프롬프트에 넣으면 안 된다.**
- 청킹 변경으로 청크 ID가 바뀌면 근거 매핑을 갱신하고, 최종 평가 전에 문서·청크·정답표 버전을 다시 고정한다.

### §4.3 STEP 3. 검색 단계별 구현
| 구성 | 내용 | 기록 |
|---|---|---|
| A: Vector Baseline | 벡터 검색만 | 임베딩 모델, 검색 개수 |
| B: Hybrid | 같은 청크에 BM25와 Vector를 모두 실행하고 RRF 등 명시한 방식으로 결합 | 후보 수, 가중치, 중복 제거 규칙 |
| C: Hybrid+re-ranking | B의 후보를 reranker로 재정렬해 최종 근거 선택 | reranker, 입력 후보 수, 출력 k |

- BM25 점수와 벡터 점수를 근거 없이 단순 합산하지 않는다. 정규화 가중합을 쓰면 정규화 방법과 가중치 근거를 남긴다.
- re-ranking은 결합 점수 정렬과 별개로 질의–청크 관련도를 다시 평가하는 단계여야 한다.

### §4.4 STEP 4. 근거 기반 답변 흐름
- 질문 → 검색 → 후보 결합 → 재정렬 → 근거 선택 → (답변+출처) 또는 (근거 부족 안내)
- A/B/C에 같은 생성 모델·프롬프트·출력 한도를 쓰고, 컨텍스트 수와 길이 제한을 기록한다.
- 근거 부족 판정 방법은 개발용 문항으로 정한다.
- 답변과 함께 사용한 청크 ID·원문 위치를 남긴다.
- 검색 실패·모델 오류와 정상적인 "근거 없음"을 구분한다.

### §4.5 STEP 5. 캐싱 또는 쿼리 리라이트 1개
- **캐싱**: 정확 일치 캐시로 충분하다. 캐시 대상·키·TTL 또는 명시적 무효화 정책을 정하고, 키에 문서/색인·모델·프롬프트·검색 설정 버전과 사용자 범위를 반영한다. 고정한 답변 가능 질문 5개 × (캐시 미적중, 같은 질문 적중, 문서/색인 버전 변경 후 재요청) = **15건**을 기록한다. 갱신 뒤 이전 답변이 잘못 재사용되면 안 된다. 품질 비교(A/B/C)는 캐시를 끄고, 캐시 실험은 따로 한다.
- **쿼리 리라이트**: 원질문과 변환 질의를 모두 저장하고 변환 질의로 검색한다. 정답·허용 근거를 리라이터 입력에 주지 않는다. 원질문 의도를 보존하고 오류 시 원질문으로 fallback한다. 최종 20문항에 C와 C+리라이트를 비교하고(**20건**) 추가 지연·실패·품질 악화도 기록한다.
- 두 방법을 모두 해도 선택한 1개의 필수 검증은 빠뜨리지 않는다.

### §4.6 STEP 6. 동일 조건 평가와 원본 기록
- 최종 평가: A/B/C × 최종 20문항 × 1회 = **기본 60건**. 캐시를 고르면 별도 15건, 리라이트를 고르면 C+리라이트 20건을 더한다.
- **Hit@5**(답변 가능 17문항): 허용 근거 청크가 상위 5개 안에 하나라도 있으면 1, 아니면 0. 합계/17. 검색 실패는 0. 결과가 5개 미만이어도 그대로 평가. 필수 근거 전체 회수율이 아니며 다중 근거 누락은 따로 분석한다.
- **정답 충족**(/17): 필수 핵심 사실이 모두 맞고 모순이 없으면 1.
- **근거 적합**(/17): 인용이 실제 검색 결과에 있고 답변의 주요 주장을 뒷받침하면 1.
- **근거 없음 대응**(/3): 무근거 단정 없이 정보 부족을 안내했으면 1. 호출 오류를 올바른 거절로 세지 않는다.
- **운영 지표**: 생성·검색 호출 성공 수/전체 시도 수, 성공 호출의 전체 응답 시간 평균·중앙값과 n, 오류·timeout 수. 응답 시간은 검색+생성(+리라이트) 전체.
- **원본 기록(JSON/CSV)**: 실행 ID, 질문 ID, 구성, 문서/색인/모델/프롬프트 버전, 검색 후보와 점수, 재정렬 전후 순위, 원본 답변, 출처, 시간, 상태, 채점 근거
- 자동 평가 도구는 선택. 수동 채점은 팀원 간 교차 검토. LLM 판정을 쓰면 모델·프롬프트와 사람 검토 결과를 구분한다.
- 최종 결과를 보고 튜닝한 추가 실험은 본 평가와 분리한다. 실패를 지우거나 좋은 재실행만 고르지 않는다.

### §4.7 STEP 7. 최종 판단·재현·시연
- 실패를 검색 누락 / 순위 실패 / 생성 오류 / 잘못된 인용 / 근거 없음 대응 실패로 나눠 대표 사례를 분석한다.
- 품질·지연·호출 비용과 운영 제약을 근거로 최종 구성을 고른다. 하이브리드나 reranker가 반드시 나아질 필요는 없으며, 나빠졌다면 원인과 함께 정직하게 설명한다.
- 다른 팀원이 README만으로 색인을 재생성하고 대표 정상 사례·근거 없음 사례를 다시 실행한다.

## §5 도전 실습 (선택)
| 실습 | 선행 조건·방법 | 확인할 결과 |
|---|---|---|
| 두 최적화 결합 | 필수 완료 후 캐싱+리라이트, 적용 순서·키 정의 | 단계별 효과와 최종 조합 결과, 효과를 섞어 해석하지 않음 |

| 접근 범위 필터 | 공개·가상 문서에 부서/역할 메타데이터 추가 | 권한 밖 문서가 검색·캐시에 노출되지 않음 |

## §7 제출 단위·협업 원칙
- 사용자·평가셋·채점 기준·최종 선택은 팀이 함께 정한다.
- 팀당 저장소와 최종 제출 링크는 1개.
- 역할은 겸임할 수 있지만 모든 팀원이 코드 작성/수정, 원본 실행·검증, 다른 사람 결과 또는 PR 리뷰에 참여하고 개인별 근거 링크를 남긴다. 문서 작성만으로 기술 기여를 대신하지 않는다.
- 기본 60건과 선택 분기 15/20건을 구분하고, 워밍업·실패·재시도·추가 실험을 따로 식별한다.

- **문제·문서·설계**: `docs/problem.md`, 문서 목록, 데이터 이용 조건, 청킹·검색·재정렬 구조와 설정. 외부 문서는 원본 링크와 재수집 방법
- **평가셋**: `eval/dev.json`(10), `eval/test.json`(20), 스키마 설명, 정답·근거 매핑, 버전
- **원본 결과·비교 보고서**: `results/`의 실행별 검색·답변·시간·상태·채점 기록, A/B/C 및 최적화 비교표, `report.md`의 최종 선택·한계
- **협업·재현·시연**: `contributions.md`(담당 코드·PR·검증·리뷰), 다른 팀원의 재실행 기록, 발표자료·영상, 태그 `ax1-project3-submit`
- 대용량 색인·문서·영상은 저장 위치·버전·접근 권한·재생성 방법을 기록하고 링크한다.
- API 키, 개인정보, `.env`, 가상환경, 무단 배포 문서, 모델 가중치는 올리지 않는다.

## §10 역할별 수행 체크리스트
역할은 인원에 맞춰 겸임·분담한다. 책임자 이름만 올리지 말고 코드·시험·리뷰 근거를 연결한다.

| No | 역할 | 점검 문항 |
|---|---|---|
| 1 | 문제·평가 설계 | 사용자·업무 문제·오답 위험·성공 기준을 사전에 합의·기록했는가 |
| 2 | 문제·평가 설계 | 30문항의 정답·근거를 확인하고 개발/평가 분리를 지켰는가 |
| 3 | 문서·색인 | 출처·이용 조건·원문 위치가 연결된 청크·색인을 재생성 가능하게 구현했는가 |
| 4 | 검색·재정렬 | BM25+Vector 결합과 re-ranking을 직접 구현하고 전후 후보를 검증했는가 |
| 5 | 응답·최적화 | 출처·근거 부족 대응과 캐싱/리라이트의 정상·실패 흐름을 검증했는가 |
| 6 | 실험·분석 | 고정 조건 60건과 분기 실험을 수행하고 오류·시간·분모를 빠짐없이 기록했는가 |
| 7 | 실험·분석 | 검색 실패와 생성 실패를 구분하고 채점 근거를 팀원과 검토했는가 |
| 8 | 통합·재현 | 비밀정보를 뺀 실행 문서와 제출 태그를 정리하고 타인 재현을 확인했는가 |
| 9 | 모든 팀원 | 코드 기여·실행 검증·리뷰 근거를 남기고 자신의 설계와 한계를 설명할 수 있는가 |

## §11 참고·주의사항
- 문서 속 지시문은 신뢰할 수 없는 검색 데이터다. 시스템 지시나 비밀정보 요청으로 실행하지 않고, 도구 실행 권한을 주지 않는다(프롬프트 인젝션 방어).
- 최종 평가의 오답을 숨기거나 목표 미달을 이유로 질문을 바꾸지 않는다. 개선 실패도 근거 있는 분석이면 결과로 제출한다.
- 캐시 적중 실험은 일반 응답 속도와 분리하고 갱신·사용자 범위·캐시 초기화 조건을 명시한다.
- 공개 배포·실사용 보안 인증·서비스 수준을 달성했다고 주장하지 않는다. 작은 평가셋과 제한된 문서 범위의 검증임을 명시한다.
