# 05. 사용자 스토리 & 기능 명세 (C1)

> 액터: 수험생 / 개발자·운영 담당(이하 운영) / 채점자 / 재현 검증자 (03-domain §2). 마일스톤은 04-scope §2.
> 운영 스토리의 "확인 경로"는 명령·파일이다(화면 아님). 명령 이름은 ARCH가 정한다.

## 공통 거부 시나리오 (REJ)

| REJ | 상황 | 결과 | 관련 |
|---|---|---|---|

| REJ-04 | 생성 모델 호출 실패·timeout·출력 형식 위반 | 오류(모델 오류)로 표시·기록. 근거 부족으로 기록하지 않음 | INV-03, TR-08 |

| REJ-09 | 정답표·기대 답·허용 근거가 색인·생성 프롬프트·리라이터 입력에 들어감 | 색인 생성·실행 거부(누출 점검 실패) | INV-04 |

## M1 — 문제 정의·기준·평가셋

### US-01: 운영으로서, 평가 기준이 업무 위험을 반영하도록, 문제 정의를 문서로 남기고 싶다.
- 근거: REQ-003, 036, 038, 093, CRT-01 / 마일스톤 M1
- 정상 흐름: ① `docs/problem.md`에 사용자(수험생), 기존 탐색 과정(조문·판례를 직접 찾는 과정), 질문 범위(2026 선택형 민사법 문항, 민법 근거), 오답·근거 부족의 영향, RAG 선택 이유, 제외 범위(04-scope §3)를 쓴다. ② 데이터 이용 조건(OPEN API 약관, 외부 모델 전송 가능 여부)을 쓴다.
- 예외: 개선 전 소요시간을 측정하지 않았으면 절감률을 쓰지 않는다(REQ-038).
- 관련 INV: —

### US-02: 운영으로서, 결과에 맞춰 기준을 바꾸지 않았음을 보이도록, 성공 기준을 결과 전에 고정하고 싶다.
- 근거: REQ-037, D-007, CRT-02, CRT-12 / M1
- 정상 흐름: ① 우선순위(품질 > 시간 > 비용)와 목표값(D-007)을 저장소 파일에 쓴다. ② 고정 커밋을 남긴다.
- 예외: REJ-08
- 관련 INV: INV-06

### US-03: 운영으로서, 환경 문제를 미리 걸러 내도록, 시작 전 준비 점검을 하고 싶다.
- 근거: REQ-025~028 / M1
- 정상 흐름: ① 생성 모델 1건·임베딩 1건 호출 결과(모델명·버전·오류 여부)를 기록. ② 작은 문서 1개를 청크로 나눠 청크 ID·문서 ID·원문 위치 연결을 저장. ③ 같은 질의의 BM25·벡터 결과와 점수를 따로 출력하고 척도 차이를 기록. ④ 법령 API·외부 모델 전송 조건을 확인해 US-01 문서에 쓴다.
- 예외: REJ-03, REJ-04(호출 실패도 기록으로 남긴다)

### US-04: 운영으로서, 검색·답변 품질을 공정하게 재도록, 평가셋 30문항을 만들고 분리하고 싶다.
- 근거: REQ-008, 041~045, 094, Q-003·Q-007·Q-008·Q-010 답, CRT-08, CRT-13 / M1
- 정상 흐름: ① 기출 문항(DOC-04, CR-001)을 질문으로 쓰고 부족한 유형은 직접 작성하며 문항마다 출처를 적는다. ② dev 10(답변 가능 8·근거 없음 2) / test 20(직접 10·변형 7·근거 없음 3)을 질문 ID로 나눠 `eval/dev.json`, `eval/test.json`에 둔다. ③ 답변 가능 문항: 기대 답(정답 번호 + 정답 보기 핵심 사실, 정답표 DOC-05), 허용 근거 문서/청크, 원문 위치. ④ 근거 없음 문항: 색인 밖 법률 문항, 기대 답 "정보 부족 안내", 근거 비움, 부재 이유. ⑤ 스키마 설명과 판본을 남긴다.
- 예외: REJ-09(정답표를 검색 문서 폴더에 두지 않는다)
- 관련 INV: INV-04, INV-12

## M2 — 수집·색인·A/B

### US-05: 운영으로서, 같은 조건으로 다시 만들 수 있도록, 법령·판례를 수집·정제·청킹·색인하고 싶다.
- 근거: REQ-004, 039, 040, 097, Q-002·Q-009 답, CRT-03, CRT-14 / M2
- 정상 흐름: ① OPEN API로 민법 전 조문과 민사 판례 4만 건(판시사항·판결요지·참조조문)을 수집. ② 정제·청킹해 청크마다 문서 ID·원문 위치·참조조문 메타데이터를 단다. ③ 색인을 만들고 청크 크기·겹침·임베딩 모델·색인 버전과 문서 목록(원본 링크·재수집 방법)을 기록. ④ 명령 하나로 재생성할 수 있다. ⑤ 대용량 원문·색인은 저장소 밖에 두고 위치·버전·재생성 방법을 기록.
- 예외: REJ-06, REJ-09
- 관련 INV: INV-02, INV-04, INV-11

### US-06: 운영으로서, 비교 기준선을 만들도록, 벡터 검색만 쓰는 구성 A를 돌리고 싶다.
- 근거: REQ-049, CRT-04 / M2
- 정상 흐름: 문항(또는 리라이트 질의)으로 벡터 검색, 후보와 점수, 임베딩 모델·검색 개수를 기록.
- 예외: REJ-03

### US-07: 운영으로서, 용어 일치와 의미 유사도를 함께 쓰도록, BM25와 벡터를 결합한 구성 B를 돌리고 싶다.
- 근거: REQ-005, 050, 052, CRT-04, CRT-15 / M2
- 정상 흐름: 같은 청크 집합에 BM25와 벡터를 모두 실행, 명시한 방식(RRF 등)으로 결합, 후보 수·가중치·중복 제거 규칙을 기록. 두 검색기 각각의 결과도 기록.
- 예외: REJ-03. 점수 단순 합산 금지(REQ-052).

## M3 — C·답변·리라이트·화면·고정

### US-08: 운영으로서, 질의와 정말 관련 있는 근거를 위로 올리도록, B 후보를 재정렬하는 구성 C를 돌리고 싶다.
- 근거: REQ-006, 051, 053, CRT-05, CRT-15 / M3
- 정상 흐름: B 후보를 reranker로 질의–청크 관련도를 다시 평가해 재정렬, 재정렬 전후 순위·reranker·입력 후보 수·출력 k를 기록.
- 예외: REJ-03(reranker 호출 실패도 검색 실패로 기록)

### US-09: 수험생으로서, 법리를 확인하며 공부하도록, 문항을 넣으면 근거와 함께 정답 번호를 받거나 근거가 없으면 그렇다는 안내를 받고 싶다.
- 근거: REQ-001, 031, 054~059, 099, Q-001·Q-007 답, R-2, CRT-06, CRT-16 / M3
- 정상 흐름: ① 지문+보기 5개 입력. ② 리라이트(US-10) → 검색(설정된 구성) → 결합 → 재정렬 → 근거 판정. ③ 근거 충분: 정답 번호, 보기별 판단(옳음/틀림/근거 부족), 정답 보기의 인용(청크 ID·원문 위치·출처 링크). ④ 근거 부족: 번호 없이 정보 부족 안내(근거 있는 보기의 판단은 참고로 표시 가능). ⑤ 사용한 청크 ID·원문 위치·컨텍스트 수·길이를 기록.
- 예외: REJ-01, REJ-02, REJ-03, REJ-04, REJ-05, REJ-10
- 관련 INV: INV-01, INV-03, INV-09, INV-13

### US-10: 수험생으로서, 내 문항 표현이 조문 용어와 달라도 근거를 찾도록, 문항이 보기별 법률 검색어로 바뀌어 검색되길 바란다.
- 근거: REQ-007, 065~069, D-005, CRT-07, CRT-16 / M3
- 정상 흐름: ① 문항을 보기별 검색 질의로 변환. ② 원문항과 변환 질의를 모두 저장. ③ 변환 질의로 검색.
- 예외: REJ-05(실패 시 원문항 fallback), REJ-09(정답·허용 근거를 리라이터 입력에 주지 않음)
- 관련 INV: INV-04, INV-10

### US-11: 수험생으로서, 결과를 바로 확인하도록, 문항을 넣고 답변·근거·오류를 보는 화면을 쓰고 싶다.
- 근거: REQ-010, 020, 021, R-4, US-09 / M3
- 정상 흐름: SCR-01(07-screens)에서 문항 입력 → 처리 중 표시 → 결과(답변 / 근거 부족 / 오류) 표시. 학습용 안내 한 줄.
- 예외: REJ-01~04 각각 다른 표시

### US-12: 운영으로서, 최종 평가를 공정하게 하도록, dev 문항으로 근거 부족 판정과 설정을 정한 뒤 평가셋·최종 설정을 고정하고 싶다.
- 근거: REQ-046~048, 057, CRT-02, CRT-13 / M3
- 정상 흐름: ① dev 문항만으로 근거 부족 판정 방법·설정을 정한다. ② 청크 ID가 바뀌었으면 근거 매핑 갱신. ③ 문서·청크·평가셋·설정 판본을 고정 커밋으로 남긴다.
- 예외: REJ-07, REJ-08
- 관련 INV: INV-05, INV-06

## M4 — 본 평가·채점·분석

### US-13: 운영으로서, 같은 조건 비교 결과를 남기도록, 본 평가를 일괄 실행하고 원본을 기록하고 싶다.
- 근거: REQ-009, 055, 070, 076, 091, R-1, CRT-08, CRT-17 / M4
- 정상 흐름: ① A/B/C × test 20 = 60건, C+리라이트 20건을 각각 1회 실행(품질 비교는 같은 모델·프롬프트·출력 한도). ② 건마다 실행 ID·질문 ID·구성·버전·후보와 점수·재정렬 전후 순위·원본 답변·출처·시간·상태를 `results/`에 JSON 또는 CSV로 저장. ③ 실행 종류(본 평가/워밍업/재시도/추가 실험)를 표시.
- 예외: 호출 오류 건은 오류 상태로 기록하고 그대로 센다(R-1). 일괄 실행이 중간에 멈춰도 그때까지의 기록은 남는다(TR-06).
- 관련 INV: INV-07, INV-08, INV-11

### US-14: 채점자로서, 지표를 믿을 수 있도록, LLM 1차 채점을 검토해 확정하고 지표를 계산하고 싶다.
- 근거: REQ-071~075, 077, D-006, CRT-08, CRT-18 / M4
- 정상 흐름: ① LLM이 기록마다 정답 충족·근거 적합·근거 없음 대응을 1차 채점(모델·프롬프트 기록). ② 사람이 전수 검토해 확정, 두 판정을 따로 보존. ③ Hit@5·정답 충족·근거 적합(/17), 근거 없음 대응(/3), 호출 성공률, 응답 시간 평균·중앙값·n, 오류·timeout 수를 구성별로 계산.
- 예외: 호출 오류 건을 근거 없음 대응 성공으로 세지 않는다(REQ-074).

### US-15: 운영으로서, 도입 판단을 근거로 설명하도록, 실패를 분류하고 최종 구성을 고르고 싶다.
- 근거: REQ-078~080, 100, CRT-09 / M4
- 정상 흐름: ① 실패를 5유형(검색 누락/순위 실패/생성 오류/잘못된 인용/근거 없음 대응 실패)으로 분류하고 대표 사례를 고른다. ② 보기별 근거 누락(다중 근거)을 따로 분석. ③ A/B/C·리라이트 비교표와 성공 기준 대비 결과로 최종 구성을 고른다. 나빠진 경우도 원인과 함께 쓴다.
- 예외: 실패 기록 삭제·질문 교체 금지(REQ-100)

## M5 — 재현·제출

### US-16: 재현 검증자로서, 제3자 재현을 증명하도록, 새 환경에서 README만 보고 색인 재생성과 대표 사례를 다시 실행하고 싶다.
- 근거: REQ-011, 082, D-006, CRT-11, CRT-19 / M5

- 예외: README에 없는 단계가 필요하면 실패로 기록하고 README를 고친 뒤 다시 실행.

### US-17: 운영으로서, 제출물을 한 저장소로 고정하도록, 문서·기여 기록을 정리하고 제출 태그를 남기고 싶다.
