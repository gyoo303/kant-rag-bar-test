# ADR-007: 원문 확보 방식 (별도 수집 파일 가져오기)
- 상태: Accepted (user, 2026-11-23) — 판례·민법 조문은 사용자가 별도 수집해 JSONL로 제공, 수집 코드는 구현하지 않음
- 관련 계층: [인프라] [모듈 협력 구조]
- 근거: AQ-010, AQ-014, TR-07, RISK-03, RISK-13, C-04, REQ-004, REQ-093, CR-002

## 맥락
법령 OPEN API는 신청·IP 등록 승인이 필요하고 호출 한도가 문서에 없다(조사 2026-11-23). 사용자가 판례 4만 건과 민법 조문을 별도로 수집해 파일로 제공하기로 했다(2026-11-23 답). 따라서 이 시스템의 범위는 "수집"이 아니라 **제공된 파일을 검증·적재(가져오기)**하는 것이다. PM US-05의 "OPEN API로 수집" 흐름은 CR-002로 바꾼다.

## 검토한 옵션
| 옵션 | 장점 | 단점 | AI 부채 영향 | 외부 기준 영향 | 되돌리기 비용 |
|---|---|---|---|---|---|
| A. 코드가 OPEN API로 수집(초당 1건 / 최대 3건 자동 감속) | 재수집이 명령 하나 | 승인 대기·한도 미확인 위험, 구현량 | 중 | CRT-03 | 낮음 |
| B. 사용자가 별도 수집한 JSONL을 가져오기 명령으로 적재(사용자 선택) | 수집 위험이 일정에서 빠짐, 구현량 작음 | 재수집 절차는 문서로만 남음(REQ-093) | 낮음 | CRT-03·14: 원본 링크·수집 방법 문서 필요 | 낮음 |

## 결정
B. 가져오기 입력 계약(이 형식이 아니면 가져오기가 거부하고 줄 번호를 보고한다):

- 위치: `data/raw/precedents/*.jsonl`, `data/raw/statutes/*.jsonl` (UTF-8, 한 줄 = 한 건, 저장소에 커밋하지 않음)
- 판례 한 줄 필드(키는 법령 OPEN API 판례 본문 필드명 그대로): `판례정보일련번호`(필수, 문자열), `사건번호`(필수), `선고일자`(필수, `YYYYMMDD`), `법원명`(필수), `사건종류명`(필수), `판시사항`, `판결요지`, `참조조문`(선택, 없으면 빈 문자열). `판시사항`과 `판결요지`가 둘 다 비면 건너뛰고 건수를 보고한다.
- 민법 조문 한 줄 필드: `법령명`(필수, "민법"), `조문번호`(필수, 정수), `조문가지번호`(선택, 정수, 없으면 0), `조문제목`(선택), `조문내용`(필수, 항·호를 포함한 조문 전체 텍스트), `시행일자`(선택, `YYYYMMDD`).
- 가져오기는 멱등이다: 같은 문서 ID는 `ON CONFLICT`로 덮어쓰고, 파일 내용 해시를 `corpus_version`에 반영한다.
- 수집 방법(누가, 언제, 어떤 조건으로 받았는지)은 사용자가 `data/MANIFEST.md`(커밋)에 적는다 — REQ-093 "재수집 방법".

## 결과
- 좋아지는 점: 2일차 위험(RISK-03) 해소, OPEN API 인증 값 불필요(`LAW_API_OC` 제거)
- 감수할 점: 제공 파일 형식이 다르면 가져오기 전에 변환이 필요(그 경우 CR, 대상 ARCH)
- 후속 작업: TKT-BE(가져오기), TKT-DB(원문 저장소), 사람: 파일 제공·MANIFEST 작성

## 쉬운 설명
- A. 코드가 직접 수집: 무엇이 달라지나 — 프로그램이 법령 사이트에서 4만 건을 받는다. / 좋은 점 — 다시 받기가 쉽다. / 감수할 점 — 사이트 승인과 호출 한도 때문에 일정이 위험하다. / 나중에 바꾸기: 보통.
- B. 직접 모은 파일을 넣기(선택): 무엇이 달라지나 — 따로 모은 판례·조문 파일을 정해진 형식으로 두면 프로그램이 검사해서 DB에 넣는다. / 좋은 점 — 수집 위험이 없어지고 만들 코드가 줄어든다. / 감수할 점 — 어떻게 모았는지를 문서로 남겨야 하고, 파일 형식이 다르면 변환이 필요하다. / 나중에 바꾸기: 쉬움.
