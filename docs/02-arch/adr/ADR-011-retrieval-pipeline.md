# ADR-011: 검색 파이프라인 (문항 분해·결합·Hit@5 목록)
- 상태: Accepted (user, 2026-11-23) — 추천안
- 관련 계층: [모듈 협력 구조]
- 근거: AQ-003, AQ-015, ASM-011, RISK-11, RISK-14, C-05, C-07, REQ-050~053, REQ-071, INV-08

## 맥락
입력은 지문 + 보기 5개다(Q-001). 보기마다 다른 조문·판례가 근거라서 문항 전체를 질의 하나로 검색하면 일부 보기의 근거가 후보에서 빠진다(RISK-11). 또 쿼리 리라이트(필수 최적화)의 효과를 C와 C+리라이트로 따로 재야 하므로(REQ-068), 리라이트가 아닌 "기본 분해"가 검색 쪽에 있어야 한다. Hit@5 정의("상위 5개 안에 허용 근거 하나")는 고정이라(C-08) 어느 목록의 상위 5개인지 정해야 한다.

## 검토한 옵션
| 옵션 | 장점 | 단점 | AI 부채 영향 | 외부 기준 영향 | 되돌리기 비용 |
|---|---|---|---|---|---|
| A. 문항 전체(지문+보기 5)를 질의 1개로 검색, 상위 k | 가장 단순·빠름 | 보기별 근거 누락 많음, 리라이트 효과와 분해 효과가 섞임 | 중 | CRT-08 해석 약함 | 낮음 |
| B. 보기별 질의 5개(질의 = 지문 요지 + 보기 원문, 규칙 기반 분해, 모델 호출 없음)로 각각 A/B/C 검색 → 보기별 최종 목록 → 라운드로빈으로 합친 "문항 목록"을 만든다. Hit@5는 문항 목록의 상위 5개로 계산 | 보기마다 근거 확보, 리라이트(C+R)는 보기별 질의를 법률 용어로 바꾸는 단계로만 더해져 효과가 분리됨 | 검색 호출 5배(로컬 검색이라 비용 작음) | 낮음 | CRT-04·05·07·08 해석 분명 | 중 |

## 계층 관점 설명
```
ExamItem ─(분해: QueryDecomposer, 규칙)→ 보기별 질의 5개
          └(C+R만) QueryRewriter: 보기별 질의 → 법률 용어 질의(실패 시 원 질의)
보기별 질의 → [A] 벡터 top N_vec
            → [B] BM25 top N_bm25 + 벡터 top N_vec → RRF(k=60) 결합·중복 제거 → top N_fuse
            → [C] B 결과 top N_fuse → reranker → top K_opt
보기별 목록 5개 → 라운드로빈 합침(보기1 1위, 보기2 1위, …, 보기1 2위 …, 중복 청크 제거) → 문항 목록
```
- 초기 값(설정 파일, dev로만 조정): `N_vec=20`, `N_bm25=20`, `N_fuse=20`, `K_opt=4`, RRF 상수 `k=60`(RRF 원 논문의 기본값). 문항 목록 길이 = 최대 20.
- Hit@5 = 문항 목록 상위 5개(= 보기마다 1위 청크)에 허용 근거가 하나라도 있으면 1. 보기별 누락은 보기별 목록으로 따로 분석(REQ-071 "다중 근거 누락").
- 생성 컨텍스트 = 보기별 상위 `K_opt`개(최대 20청크). A/B/C 모두 같은 `K_opt`·같은 프롬프트(INV-08).

## 결정
결정: B — 문항 통째 입력에서 보기별 근거를 찾고, 리라이트 효과를 따로 잴 수 있는 유일한 구조다.

## 결과
- 좋아지는 점: 보기별 근거 확보, A/B/C·리라이트 비교가 한 변수만 바뀜
- 감수할 점: 검색 5회/문항, 컨텍스트가 길어짐(시간·비용 증가)
- 후속 작업: A4 `QueryDecomposer`·`HybridRetriever`·`Reranker` 시그니처, A5 SEQ

## 쉬운 설명
- A. 문항 전체로 한 번 검색: 무엇이 달라지나 — 지문과 보기를 통째로 한 번 검색한다. / 좋은 점 — 가장 빠르고 단순하다. / 감수할 점 — 보기 5개 중 일부는 근거를 못 찾기 쉽고, 리라이트 효과를 따로 보기 어렵다. / 나중에 바꾸기: 쉬움.
- B. 보기마다 따로 검색 후 합치기: 무엇이 달라지나 — 보기 5개를 각각 검색하고, 보기마다 가장 관련 높은 근거를 번갈아 모아 문항 하나의 근거 목록을 만든다. / 좋은 점 — 보기마다 근거를 찾고, 리라이트를 켰을 때와 껐을 때 차이를 정확히 비교할 수 있다. / 감수할 점 — 검색을 5번 하고 답변에 넣는 근거가 길어진다. / 나중에 바꾸기: 보통.
- 추천: B — 이 프로젝트의 입력(문항 통째)과 평가 방식에 맞는 구조다.

## 개정
- 2026-11-25 (CR-018): **조문 몫 보장**을 더했다. 보기별 검색 결과의 상위 `k_opt` 안에 조문(`STATUTE_ARTICLE`)이 `k_law`개 미만이면, ① 목록 아래쪽 조문을 끌어올리고 ② 그래도 모자라면 같은 질의로 **조문만** 검색해 채운다(`StatuteQuotaRetriever`). 채우는 자리는 상위 `k_opt` 안에서 순위가 가장 낮은 판례를 밀어낸다. 모든 구성(A·B·C·C+R)에 같은 방식으로 적용한다(INV-08). `k_law`는 `comparable_key`에 들어간다.
  - 근거: 말뭉치가 판례 35,831 대 조문 4,265(판례 89%)라 조문이 점수 경쟁에서 묻힌다. 2026 선택형 재측정에서 틀린 10문항의 조문 비율이 3.8%(맞힌 60문항 9.5%)였고 7문항은 조문 0개였는데, 필요한 조문(민법 제507조 혼동, 제587조 과실의 귀속)은 색인에 있었다 — 순위 문제다.
  - **한계(실측)**: 몫은 조문의 *존재*를 보장할 뿐 *적합성*은 보장하지 않는다. 보충 검색도 같은 질의를 쓰므로, 질의가 명제를 제대로 담지 못하면 엉뚱한 조문이 들어온다. 질의 품질은 CR-018의 범위 밖이다.
- 2026-11-25 (CR-020): **명제 단위 질의 분해**. 지문에 줄 머리 `ㄱ.`·`ㄴ.` 표시가 2개 이상이면 조합형으로 보고 보기가 아니라 명제마다 질의 하나를 만든다(슬롯 1~N, 남는 슬롯은 지문의 물음 문장). 조합형에서는 `OptionQuery.option_no`가 보기 번호가 아니라 질의 슬롯 번호다. 근거: 조합형 보기는 "ㄱ, ㄴ"(6자)뿐이라 보기별 질의 5개의 원문이 사실상 같아진다 — 조합형 후보 중앙값 11(최소 4) 대 일반형 17.5(최소 12), 틀린 10문항이 전부 조합형.
